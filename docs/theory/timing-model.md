# 时序模型

> **定位**：Storyloom 时序设计的理论基础。不涉及具体实现，只描述度量标准、延迟结构及架构推论。
>
> **对应核心问题**：② 消解生成延迟（分析层）。

---

## §1 度量标准

LLM 推理需要时间。衡量这段等待有两个不同的视角：

| 指标 | 关注点 | 后果 |
|------|--------|------|
| **总生成时间** | 全部内容何时产出 | 必须等全部完成 → 全量解析 → 用户等待 = 总时间 |
| **首 token 时间（TTFT）** | 第一个可展示内容何时可用 | 首片段即可展示 → 增量解析 → 用户等待 ≈ TTFT |

选择 TTFT 作为衡量标准，意味着必须采用增量（流式）解析——不等全部生成完毕，边生成边展示。全量解析在架构层面将等待时间从 TTFT 拉长到总生成时间，破坏了延迟隐藏的前提。**增量解析不是性能优化，是正确性要求。**

## §2 延迟的影响因素

LLM 推理延迟由两部分组成：**首 token 时间（TTFT）** 和 **逐 token 生成时间**。

关键事实（实验验证）：输出长度对 TTFT 的影响在一定范围内极低。输出增加数倍，TTFT 增幅仅百分之几十。TTFT 的主要影响因素是输入复杂度（Prompt 大小与结构），而非输出长度。

这意味着：

- **优化方向是提示词设计**，而非缩短输出——减少输出长度对降低 TTFT 收效甚微
- **输出长度是廉价的**——可以在一定范围内要求更长的输出，为桥接预留更多缓冲空间，而不过度影响等待时间

---

## §3 三层流与双队列

从数据产生到用户消费，存在三个速度层：

```
生成流（LLM）  →  解析流（程序）  →  展示流（UI）
 慢/不可控          快/可控             按人类节奏/可控
```

基本不等式 `T_gen ≥ T_parse ≥ T_display`：生成 ≥ 解析是物理约束（无数据可解析），解析 ≥ 展示是正确性约束（无内容可展示）。

三层之间存在两个速度断层：

| 断层 | 速度差 | 问题 |
|------|--------|------|
| 生成 ↔ 解析 | 秒级 ↔ 微秒级 | 解析总是在等生成 |
| 解析 ↔ 展示 | 微秒级 ↔ 秒级 | 展示按自身节奏，不能被推送速度强迫 |

每个断层必须插入缓冲队列——否则三层耦合在一起互相阻塞。这是**双队列架构**的理论依据：

- **队列①（生成↔解析）**：解耦 LLM 产出与程序解析。使能**后台预取**——桥接机制的物理前提。
- **队列②（解析↔展示）**：解耦解析速度与展示节奏。使能**引擎-UI 分离**——引擎产出事件流，UI 按自身节奏消费。

> 队列的具体实现属于工程选择。但**在两个速度断层处各需要一个缓冲层**，是三层流速度差的直接推论，与实现无关。

---

## §4 架构推论

时序模型对流式架构提出三条**格式无关的**约束：

1. **内容格式必须支持逐片段独立解析**——不能要求完整内容才能开始解析
2. **解析器必须能在不完整输入下产出有效事件**——不能等"全部完成"
3. **生产与消费之间需要缓冲层**——解耦不可控的生成与可控的消费

不满足这三条的架构，在时序模型下不可行。具体格式和缓冲实现是工程选择，会随技术演进而变化。
