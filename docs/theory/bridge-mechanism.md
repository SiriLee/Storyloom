# 桥接机制

> **定位**：Storyloom 消解生成延迟的核心方案。不涉及具体实现，只描述思想、可行性条件及设计约束。
>
> **对应核心问题**：② 消解生成延迟（解决层）。

---

## §1 核心思想

延迟客观存在且无法消除，但"延迟"和"等待感"是两回事。唯一不需要更快 LLM 的方案：**让生成发生在用户消费内容的时候，而非等待的时候**。

实现方式：每轮 LLM 输出被一个标记点分为两个区域：

| 区域 | 内容 | 消费方式 |
|------|------|---------|
| **交互区**（标记前） | 核心内容 + 输入 + 状态变化 + 路由 | 用户主动消费——体验、判断、选择 |
| **缓冲区**（标记后） | 无交互内容，仅用于缓冲 | 用户被动消费，程序极快穿越——无需等待反馈 |

程序在穿越缓冲区时立即发起下一轮请求。当用户消费完缓冲区、做出选择时，下一轮已就绪或接近就绪。

---

## §2 可行性条件

桥接不是独立成立的——依赖三层前提，缺一不可：

1. **增量解析**（来自时序模型 §1）：全量解析使首个可展示内容的时间 = 总生成时间，没有"用户消费时后台生成"的窗口。增量解析使交互区边生成边展示，创造时序重叠的前提。

2. **TTFT < 缓冲区展示时长**：下一轮的首 token 必须在缓冲区被消费完之前到达。TTFT 过长则不等式不成立，等待感出现。

3. **足够的缓冲量**：缓冲区必须能覆盖典型 TTFT。太少覆盖不了，太多挤压交互区空间。标记位置是受 TTFT 约束的权衡——会随模型速度变化，属于工程调参范畴。

---

## §3 设计约束

以下约束从核心思想直接推导，与具体实现无关：

1. **标记恰好出现一次**——零次无缓冲（等待暴露），多次语义混乱
2. **标记之后禁止交互元素**——否则缓冲区无法被快速穿越，时序重叠被破坏
3. **标记之前完成所有交互声明**——选项、状态变更、路由必须在交互区内完成

---

## §4 作为合成点

桥接是各设计维度的汇合点：

- **时序模型**定义了"为什么必须流式"
- **双队列**的队列①（生成↔解析断层）是后台预取的物理前提
- **输出格式**提供表达分界标记的语法
- **上下文管理**控制 Prompt 大小，使 TTFT 约束得以满足

如果桥接被证明不可行（如 TTFT 无论如何无法被缓冲区覆盖），则项目的基础假设需要重新审视。
