## §1 总览

### 1.1 术语速查

**共创与大纲**

| 术语 | 含义 | 详见 |
|------|------|------|
| **story_config** | 共创阶段产出的故事设定（tier、title、language、premise） | §3.4 |
| **大纲 (outline)** | 由关键节点组成的有向图，描述故事骨架。节点间可有分支 | §3.6 |
| **变量定义 (variables)** | 共创阶段 LLM 自定义的游戏变量列表，顶层存储。每项含名称、类型、初始值 | §3.4 |
| **冒险日志 (adventure_log)** | 结局时独立 LLM 调用生成，不走正常叙事循环 | §5.4 |

**剧情段与路由**

| 术语 | 含义 | 详见 |
|------|------|------|
| **剧情段** | 每轮 LLM 生成的一段叙事文本，为循环基本单位 | §4 |
| **关键节点 (checkpoint)** | 大纲上的里程碑节点。到达时触发进度推进和自动存档 | [data-model.md](./data-model.md) |
| **段内分支** | 同一剧情段内的叙事分支，不一定影响大纲走向 | [block-spec.md](./block-spec.md) |
| **大纲分支** | 大纲层面的分叉路线，通过 `if -> route` 实现 | [block-spec.md](./block-spec.md) |
| **bridge** | `<bridge/>` 自闭合 XML 元素，标记下一轮 Prompt 组装触发点 | [block-spec.md](./block-spec.md) |
| **bridge_text** | `<bridge/>` 之后至 `</story>` 的纯文本内容，作为下一轮 User Message 中的 bridge_text 字段 | [block-spec.md](./block-spec.md) |
| **XML 元素** | LLM 输出使用 XML 格式，根元素 `<story>`，内含 `<seg>`/`<choice>`/`<checkpoint>`/`<branch>`等 | [block-spec.md](./block-spec.md) |
| **current_branch** | 当前段内分支名，决定程序匹配哪些命名区块 | [block-spec.md](./block-spec.md) |
| **choice_dict** | 本轮选项结果，key 为 `choice:` 声明值 | [block-spec.md](./block-spec.md) |

**状态与存档**

| 术语 | 含义 | 详见 |
|------|------|------|
| **状态变量 (state_vars)** | 游戏内可变数据，由共创阶段 variables 定义初始化 | [data-model.md](./data-model.md) |
| **GameState** | 程序内存中维护的完整游戏状态 | [data-model.md](./data-model.md) |
| **rejected_changes** | 被校验拒绝的 state 变更条目 | [block-spec.md](./block-spec.md) |
| **游戏存档** | `saves/` 下的游戏存档与游戏节点存档 | [data-model.md](./data-model.md) |

### 1.2 程序生命周期总览

```
启动（验证凭证）
  │
  ▼
新游戏 → 共创 → init GameState → 叙事循环(N轮) → 结局 → 返回
  │
  ▼
读档/继续 → 选档 → restore GameState → 叙事循环(N轮) → 结局 → 返回
```

### 1.3 核心原则

> 以下原则贯穿 Phase 1 全部流程。

| 原则 | 说明 |
|------|------|
| **AI 实时生成内容(基础)** | AI 实时生成是项目的建立基础 |
| **用户体验无缝衔接(核心)** | bridge 标记触发提前请求，用户体感不感知段边界 |
| **本地数据为唯一真相源** | 一切游戏数据以本地 GameState 为准。LLM 只能*建议*变更 |
| **bridge 之后无底层数据变更** | bridge 之后不得出现交互、变更类型区块 |
| **交互内容前置于 bridge** | 交互和变更区块集中在段前部，bridge 之后为纯叙事缓冲 |
| **程序拥有最终控制权** | API 失败、解析错误、内容异常——告知用户并等待决策 |

## §2 程序生命周期

### 2.1 启动

程序启动时验证 API 凭证可用。不验证凭证有效性（首次 API 调用时暴露），不预先创建存档目录（首次写入时创建）。

### 2.2 生命周期阶段

- **新游戏**：进入共创阶段，产出故事数据 → 初始化 `GameState` → 进入叙事循环。每次新游戏创建独立的存档目录。
- **继续**：选取最近游玩的存档，进入“读取存档”步骤。
- **读取存档**：从存档列表中选择游戏和存档文件 → 校验完整性 → 恢复 `GameState` → 进入叙事循环。
- **存档管理**：浏览/删除存档文件——由 UI 层实现，引擎提供 `list_games()`、`delete_save()` 等 API。

## §3 共创阶段

### 3.1 阶段总览

```
Step 1：用户输入初始想法
      ↓
Step 2: 自由对话
（LLM 询问为主，同一对话上下文累积）
      ↓ 用户决定开始
Step 3: 生成故事
（单次 LLM 调用，产出设定、角色、大纲等）
      ↓ 产出元存档
Step 4: 初始化（与读档流程相同）
（存档 → GameState → 叙事循环）
```

### 3.2 Step 1: 用户输入初始想法

```
程序打印：
  "请描述你想玩的故事（如'赛博朋克背景下的爱情故事'）"

用户输入自由文本 → raw_idea
```

无校验——任何非空文本均接受。空输入提示重新输入。

### 3.3 Step 2: 自由对话

**流程**：

```
将 raw_idea 发送给 LLM（追问 Prompt）
    │
    ▼
┌────────────────────────────────────────────┐
│ 循环：                                       │
│   LLM 回复（提问 + 可选参考选项）               │
│   → 程序展示回复                              │
│   → 用户回复                                  │
│   → 追加到对话历史                             │
│   → 用户通过 UI 命令决定退出或进入生成阶段       │
└────────────────────────────────────────────┘
```

**终止条件**：

| 条件 | 行为 |
|------|------|
| 用户通过 UI 触发生成（如 `/go`、点击按钮等） | → 进入 Step 3 |
| 用户通过 UI 触发退出（如 `/quit`） | → 返回主菜单 |

> 对话自然进行，直到用户决定开始生成。

> **追问范围约束**：LLM 可参考以下维度引导对话——世界观、主角设定（姓名、性别、身份、性格、背景）、故事基调、冲突方向、故事长度。但这不是硬性清单，LLM 应根据对话自然流动灵活探索。严格禁止涉及具体情节走向或透露后续内容。

### 3.4 Step 3: 生成故事

UI 触发生成 → 引擎注入生成 Prompt ，单次 LLM 调用产出完整故事数据的 JSON 对象。

**流程**：

```
1. 程序展示等待文案

2. 引擎将生成 Prompt 作为 user 消息追加到对话历史
   → LLM 返回一个 JSON 对象

3. JSON 解析：
   ├── 成功 → 继续校验
   └── 失败 → 向 LLM 反馈，可重试

4. 逐部分校验：
   ├── 字段完整性
   ├── 约束合规性
   ├── 引用有效性
   └── 失败 → 向 LLM 反馈具体字段错误，可重试

5. 全部通过 → 返回生成结果
   API 失败 / 校验失败 → 向 UI 报告，由用户选择重试或退出
```

### 3.5 Step 4: 初始化 GameState

> GameState 完整结构定义见 [`data-model.md`](./data-model.md)。

校验通过后，从（元）存档中提取各部分数据初始化 GameState：故事设定、角色列表、地点列表、变量定义、大纲等。

初始化后进入叙事循环（§4）。

## §4 叙事循环

### 4.1 单轮总览

> **引擎视角**：以下阶段描述引擎侧每轮的工作内容。引擎通过事件流向 UI 提供数据，不直接控制展示节奏。

```
Round N 开始
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 1. TTFT 等待                                          │
│   UI 展示上一轮 bridge_text（首轮无）；引擎等待 API     │
│   返回第一个 token。TTFT 通常 10-30s。                 │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 2. <story> 开始                                       │
│   流式解析器收到 <story> 标签——解析生命周期             │
│   正式入口。触发故事开始事件。                          │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 3. 流式解析（§4.4）                                   │
│   逐行解析：                                          │
│   • Pre-bridge：正常处理各类标签                       │
│   • 遇到 choice：发送事件给 UI，等待玩家输入            │
│   • segment 文本实时以事件形式发给 UI                  │
│   • UI 层使用队列缓冲——非阻塞接收，按自身节奏展示        │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 4. <bridge/> — 模式切换                               │
│   • 解析器切换到 post-bridge 模式                      │
│   • 后续内容快速解析（纯叙事，无 UI 反馈等待）           │
│   • post-bridge 违规元素记入格式错误记录，不传给 UI     │
│   • bridge_text 按分支归属累积（§4.7）                 │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 5. </story> — 解析完成，打包 + 发送（§4.7）            │
│   • 合并格式错误（解析器采集 + checkpoint 校验）        │
│   • 自动推进 + 非结局：组装下轮 Prompt → 后台 API 调用  │
│   • 结局：组装冒险日志 Prompt → 后台 API 调用（§5）     │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 6. 错误处理（两级）                                    │
│   • 严重（API 失败 / 解析失败）：通知 UI → 用户决策     │
│   • 普通（格式错误 / 状态拒绝）：程序内部处理            │
└──────────────────────────────────────────────────────┘
```

> LLM 响应使用 `StreamingXmlParser` 逐行流式解析（见 §4.4）。流式解析的必要性见 §4.3。XML 元素语法、分支路由、状态校验的完整规则见 [`block-spec.md`](./block-spec.md)。节点推进与存档见 [`data-model.md`](./data-model.md)。

### 4.1.1 错误严重等级分类

引擎侧对所有异常采用两级分类，决定处置策略和 UI 通知方式：

| 等级 | 范畴 | 处理策略 | UI 行为 | 示例 |
|------|------|---------|---------|------|
| **严重** | 影响本轮可用性的致命故障 | 停止当前处理，通知 UI，**由用户决策** | 展示错误信息，等待用户选择（重试 / 返回） | API 网络错误、响应完全无法解析、流式超时 |
| **普通** | 不影响本轮展示的可恢复问题 | **程序内部处理**，不在当前轮打断用户体验 | 不展示给用户，仅在下一轮 Prompt 中反馈 | 格式错误（post-bridge 违规元素）、状态变更被拒绝、行号偏差 |

**严重错误的用户决策路径**：

```
API 错误 / 解析失败 / 流式超时
    → 通知 UI 具体错误信息
    → 用户选择：
      ├── 重试：重新发送相同 Prompt（引擎保存原始消息，UI 调用 retry()）
      └── 返回主菜单：放弃本轮，回到主菜单
```

> **关键原则**：依赖 API 调用的错误**不自动重试**——始终由用户决策。程序只提供信息和选项，不做自动恢复。

### 4.2 每轮 Prompt 的组成

采用对话式消息数组架构。完整规范见 [`prompt-design.md` §4](./prompt-design.md)。

**要点**：Round 1 前缀永久锚定（含角色定义、XML 格式规范、格式示例、核心规则等）——永不压缩、永不删除。Round N 轻量上下文（大纲进度、当前状态、bridge_text、错误反馈等）——不含格式规范。

### 4.3 API 调用与响应接收

**流式接收与 bridge 时序**：

bridge 机制依赖流式 API。当程序解析到 `<bridge/>`，切换模式并快速处理。解析到 `</story>` 时，立即在后台线程发起下一轮 API 调用 — 同时继续展示 post-bridge 段落（bridge_text）。后台响应在 bridge_text 展示期间到达并缓冲，用户体感上无段边界停顿。

这意味着 bridge 机制的真正时限不是 LLM 总生成时间，而是后台 API 调用的 TTFT + 生成时间 vs. bridge_text 的展示时长。

> **流式解析要求**：所有轮次使用流式解析器逐行解析。全量解析要求全部行生成完毕才能展示首段（TTFT + 生成 ≈ 35-80s），流式解析仅需首行（TTFT + 首行 ≈ 10-30s）。bridge_text 阅读时间（10-20s）可覆盖 TTFT 但不可覆盖完整生成——全量解析在该模式下大概率导致空白等待。

> **关键**：TTFT 主要受 Prompt 复杂度影响，而非内容输出长度。优化 System Prompt 可显著缩短 TTFT。

**流程**：

```
1. 上下文管理器获取当前 messages 数组
2. 提示词构建器追加当前轮 user 消息
3. 将完整 messages 数组发送至 API（流式）
   │
   ├── 正常完成 → 完整 LLM 响应文本
   │
   ├── 流式停顿超时
   │   └── 视为严重错误 → 保存原始消息用于重试
   │       → 发送事件通知 UI
   │       → 用户选择
   │
   └── API 错误
       └── 告知用户具体错误信息
           → 用户选择：重试 / 返回主菜单
```

> API 调用失败**不自动重试**，始终由用户决策。

**三层时序模型**：

```
LLM 生成流（token 产出）
    ≥
程序解析流（解析器逐行解析）
    ≥
UI 展示流（用户阅读 / 自动推进）
```

| 流 | 负责层 | 说明 |
|------|---------|------|
| LLM 生成流 | API 服务端 | token 逐块产出，TTFT 10-30s + 生成 25-50s |
| 程序解析流 | 引擎 | 逐行流式解析，通常与生成流几乎同步（生成即解析） |
| UI 展示流 | UI 层 | 消费引擎产出的事件，按自身节奏展示 |

**流间同步规则**：

- **生成→解析**：通常同步。token 到达后经流式解析器逐行处理，产出事件。**例外**：选择点处解析流暂停等待 UI 反馈（玩家输入），之后继续快速解析。
- **解析→展示**：基本不同步。**例外**：选择点处解析流暂停等待 UI 反馈，逐渐趋于同步，之后继续维护各自流程。
- **bridge→`</story>` 区间**：解析流**不需要等待 UI 反馈**——bridge_text 仅含纯叙事，无交互元素。解析此区间极快（微秒级）。

> **关键洞察**：程序解析到 `<bridge/>` 时，LLM 生成流通常已完成 bridge_text 内容的产出（生成流领先于解析流）。因此 bridge→`</story>`→pre-fetch 启动这一路径在引擎侧是**几乎不间断的同步执行**。引擎在 `</story>`（解析完成）处立即组装 Prompt 并启动后台 API 调用。

> **预解析机制建议**：在生成→解析阶段可以加入“预解析”，此流程不依赖选择点处的等待，为后续图像功能拓展做准备。

### 4.4 响应解析

利用 `NNN| ` 行号前缀使每行成为自包含的 XML 片段，逐行正则匹配产出事件，不等完整文档。

```
1. 预处理：剥离 NNN| 前缀 → 跳过空行和注释

2. 逐行正则匹配 → 发送事件

3. 解析过程中同步累积结构化数据
```

> **各元素语法**：见 [`block-spec.md`](./block-spec.md) §4。

### 4.5 内容展示

**展示模式**：支持自动和手动两种，用户可随时切换。

| 模式 | 行为 |
|------|------|
| **自动** | 每段之间以固定间隔自动继续 |
| **手动** | 每段展示后等待用户确认继续 |

> 默认模式由 UI 层决定，用户可随时切换。

**展示流程**：

```
1. 从展示队列取匹配 current_branch 的正文
2. 按数字编号分割为展示段（见 block-spec.md §2）
3. 剥离编号前缀，逐段展示纯文本：
   ├── 自动模式：逐段展示，固定间隔后自动继续
   └── 手动模式：逐段展示，等待用户确认后继续

4. narrative 展示完毕后：
   ├── 有 <choice>？→ 展示选项面板（§4.6）
   └── 无 → 展示 bridge_text → 自动进入下一轮
```

**bridge_text 展示**：`<bridge/>` 之后的 `<seg>` 和 `<branch>` 内的 `<seg>` 按元素边界分割展示。用户无感知——体感上是连续叙事。

**命名 narrative 展示**：遍历时仅 `current_branch` 匹配的 narrative 进入展示队列。

> **UI 队列缓冲模式（推荐）**：
> - **接收侧**：非阻塞地从引擎侧接受事件，立即放入内部队列
> - **展示侧**：按自身节奏从队列取出并展示（固定间隔 / 用户确认）

### 4.6 玩家交互

**选项展示**：

```
  [1] 接过芯片                        ← 正常可选
  [2] 暂时离开（理智值≥30）          ← （当前：20）不可选
  [3] 先发制人                        ← 正常可选
```

**选项处理**：

选项可附带条件（`if` 属性）。条件评估由引擎统一完成————直接告诉 UI 每个选项是否可选以及不满足条件时的展示文案。UI 只负责根据引擎的结论渲染——不可选的项目置灰，用户误触时本地提示重新选择。

当选项全部不可选时，引擎将全部恢复为可选并标记兜底状态，防止游戏卡死。

### 4.7 下一轮准备与结局检测

`<bridge/>` 元素具有**双重角色**：

**对 LLM 的结构约束**（主要方面）：
- 标记交互区与叙事区的硬分界——bridge 之后严格禁止 `<choice>`、`<set>`、`<checkpoint>`
- 强制 LLM 在交互断点之前完成所有状态变更和路由声明
- Post-bridge 仅提供叙事缓冲（`<seg>`、`<branch>`），为下一轮 Prompt 组装争取时间

**对程序的行为切换**（桥接解析阶段）：
- **模式切换**：解析器从"交互+叙事"模式切换到"纯叙事"模式（post-bridge 模式）
- **快速解析**：Post-bridge 区间无交互元素，不需要等待 UI 反馈，全速解析
- **错误捕获**：Post-bridge 区间出现的 `<choice>`/`<set>`/`<checkpoint>` 记入格式错误记录，不传递给 UI
- **bridge_text 捕获**：Post-bridge 的 `<seg>` 文本按 `current_branch` 过滤后存储，注入下一轮 Prompt

**Prompt 组装与 Pre-fetch 触发**：

程序的实际触发点是**解析完成**（`</story>`），而非 `<bridge/>` 本身。但 bridge→`</story>` 区间解析极快（纯叙事、无 UI 阻塞），两者可视为几乎同时：

```
解析到 <bridge/>
    │  ← 模式切换（微秒级）
    │  ← 快速解析 post-bridge 内容（微秒级，无 UI 反馈等待）
    ▼
解析到 </story>（解析完成）
    │
    ├── ending_flag == true？
    │   └── 是 → 组装冒险日志 Prompt（§5.4）→ 发 LLM → 继续展示 bridge_text
    │           → bridge_text 展示完毕 + 响应就绪 → 展示 adventure_log → 返回主菜单
    │
    └── 否 → 正常准备：
        1. bridge_text 提取（见 block-spec.md §4 `<bridge/>` 节）
        2. round_count += 1
        3. 组装下一轮 Prompt → 启动后台 API 调用 → Round N+1
```

> `ending_flag` 由 checkpoint 的 routes 为空（结局节点）时设置（见 data-model.md）。

## §5 结局阶段

### 5.1 结局触发路径

| 路径 | 触发条件 | 说明 |
|------|---------|------|
| **自然结局** | checkpoint 的 routes 为空（结局节点） | 大纲终点，最后一轮由 LLM 自然收束 |
| **主动结束** | 玩家通过 UI 触发提前结束 | 随时中断，跳过后续大纲 |

### 5.2 自然结局流程

结局节点通过 routes 为空的关键节点来判定。

```
倒数第二轮（Round N-1）：
  <story>
  （结局叙事段落……）
  <checkpoint ...>
  （结局叙事段落……）
  <bridge/>
  （最后的衔接文本——缓冲用，保持与正常剧情段一致的结构）
  </story>

程序处理：

  1. 正常解析
  2. 处理 checkpoint：
     a. routes 为空 → 检测为结局节点
     b. 设置 ending_flag = true
     c. 触发自动存档（与其他 checkpoint 行为一致）
  3. 执行到 </story>：
     a. 检测到 ending_flag == true
     b. 组装"冒险日志 Prompt"（§5.4）
     c. 发送给 LLM → 等待响应
  4. 继续展示 bridge_text（缓冲叙事）——与正常轮次无差异
  5. bridge_text 展示完毕 + LLM 响应就绪：
     → 展示 adventure_log 内容
     → 等待用户返回主菜单
```

> **关键**：结局节点由 routes 为空判定。程序检测到 ending_flag，提交冒险日志请求。尾部 bridge_text 作为缓冲。

### 5.3 主动结束流程

玩家通过 UI 触发提前结束（如快捷键、按钮等）：

主动结束不生成冒险日志——冒险日志回顾的是已完成的故事弧线，中途退出没有闭合语义。存档照常保留，玩家随时可"继续"回到退出点。

### 5.4 冒险日志 Prompt

**触发时机**：结局轮 `<bridge/>`/`</story>` 处。

> 冒险日志为独立 LLM 调用——不走正常叙事循环的解析管线。Prompt 模板与示例见 [`prompt-design.md` §5](./prompt-design.md)。
