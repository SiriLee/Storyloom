## §1 背景

现行输出协议（`NNN| ` 行号前缀 + XML 元素）是反复迭代、实测验证的产物（正确率 20-74% → 100% 的教训），但存在三个结构性限制：

1. **每轮要求 LLM 现场学习格式规范**——行号规则、标签语法、转义约定均需注入 Prompt，对 TTFT 与输出正确率均有影响；而其中部分元素（存档点、桥接标记）是程序的必然要求，无法省略。
2. **内容可规范性与可拓展性受限**——视觉小说元素众多（音频、特效、表情、语音等），现行格式覆盖有限；且格式是本地设计而非业界经验范式，不稳定因素多的格式不利于未来可能的专用模型设计。
3. **素材管线的阻塞时机未达理论最优**——素材声明的等待发生在声明点附近，浪费了声明点与使用点之间的阅读消费缓冲。

> 背景补充：项目当前无发布宣传与用户包袱，处于"协议可自由重构"的最佳窗口期。追求最优而非兼容性。

## §2 设计决策总览

三个决策构成统一的协议层重构，相互加强：

| # | 决策 | 一句话 |
|---|------|--------|
| 一 | 轮 = 节点 = 存档点 | 每轮必含一个存档节点，总长由共创阶段完全决定 |
| 二 | 素材声明不阻塞 | 声明只启动生成，阻塞只发生在素材被实际使用的时刻 |
| 三 | 输出格式 = 类 Python 调用脚本 | LLM 输出一段白名单调用序列，引擎解释执行 |

**统一叙事**：每轮 = 一段受限 Python 调用脚本，引擎解释执行；素材声明不阻塞、checkpoint 必含、bridge 收尾。

---

## §3 决策一：轮 = 节点 = 存档点

### 3.1 动机

- 总长控制从 Prompt 软约束升级为结构硬约束（轮数 = 大纲节点数），故事实际长度由共创阶段完全决定。
- 消除已知缺陷：现行压缩机制仅收集带 checkpoint 摘要的轮次，无 checkpoint 的轮次滑出窗口后细节丢失。
- 减轻 LLM 负担：节点推进由引擎权威判定，LLM 无需输出节点 ID 等机械信息，只承担叙事与摘要职责。
- 基于观察：**LLM 输出总长增长对 TTFT 增长的影响较小**（TTFT 主要受 Prompt 复杂度影响）——放开长度上限的代价可控，且可换取更大的轮内/轮间缓冲余地。
- 来源参考：竞品以"场景"为单位区分轮次的设计，与"节点 = 轮"对齐。

### 3.2 决策要点

- 每一轮必须包含且仅包含一个存档节点（checkpoint）。
- 不再要求 LLM 显式输出行号——位置追踪由引擎自记（素材匹配等依赖行号的对齐逻辑不受影响）。
- 叙事缓冲区（bridge_text）长度放开为"大致长度、多多益善"，不设硬上限。
- **上下文管理随轮语义调整**：轮次总数减少、单轮内容量增大，滑动窗口与压缩机制需相应调整（窗口规模、摘要粒度、token 预算的重新配比）。

### 3.3 不变量

- 每轮恰好推进一个节点；节点归属与推进由**引擎权威判定**，LLM 只是建议者。
- 每轮必有节点摘要——摘要永不缺失，是压缩机制与未来记忆能力的原料。
- 存档语义 = 节点边界；加载后从节点全新开始，不携带旧轮衔接文本。
- 节点推进失败或缺失时按"本地数据唯一真相源"原则兜底（引擎判定 + 下轮反馈），不中断游戏。

### 3.4 验收标准

- 任意档位（short / medium / long）故事跑完，总轮数 = 大纲节点数（允许定义可容忍误差）。
- 长局（≥ 20 节点）下上下文 token 预算稳定不溢出。
- 压缩摘要完整覆盖全部历史节点，无缺失。
- 存档 / 读档 / 续玩跨节点正确。

## §4 决策二：素材声明不阻塞事件分发

### 4.1 动机

- 现行语义下素材声明触发强制等待，阻塞发生在声明后第一个事件——因此设计中"声明靠近使用点"成为必然（用用户阅读缓冲隐藏等待）。
- 实际最优策略：声明只登记启动生成；**只有真正使用到对应素材、且未生成完毕时才执行等待**。
- 最大化利用阅读消费缓冲——这是"实时生成"前提下的最大可用缓冲空间，是对素材生成理论（素材必须在展示前完成，不必在需求识别前完成）的更忠实实现。

### 4.2 决策要点

- 素材声明永不阻塞事件分发。
- 阻塞只可能发生在"素材被实际引用且未就绪"的使用点。
- 声明时机从"靠近使用点"反转为"越早越好"（跨轮同样成立：上轮声明、下轮使用，完全异步覆盖）。

### 4.3 不变量

- 事件分发器在声明处不等待；等待仅发生在使用点，且必须有显式超时兜底——超时走占位素材并反馈，游戏永不卡死。
- 素材生成可跨轮：声明与使用允许跨越轮边界，进行中的任务不被轮末清理误杀。
- 文本模式行为零变化（素材管线仅存在于图模式）。

### 4.4 验收标准

- 声明点至使用点之间的全部阅读缓冲被利用（使用点素材就绪率可度量提升）。
- 素材生成超时场景下管线无卡死，有占位展示与反馈机制。
- 轮末进行中的任务正确跨轮继续，无泄漏、无重复生成。
- 文本模式回归全绿。

## §5 决策三：输出格式 = 受限调用脚本

### 5.1 动机

- 函数签名即规范：调用形态自带全部约束，LLM few-shot 后零学习成本，格式正确率上限最高。
- **类 Python 调用形态**是 LLM 训练语料中最熟悉的表达，相比自造格式（行号 + XML）是"先验熟悉度"的最优解——直接降低每轮"现场学习格式"的认知负担与 TTFT 影响。
- **Ren'Py 词汇参考**：Ren'Py 是业界二十年打磨的视觉小说语义全集，以其为词汇与范围参考保证规范性、全面性，并为未来专用模型对齐业界。
- 为未来能力铺路：格式约束解码、专用模型微调、原生函数调用平移均以此为地基。

### 5.2 决策要点

- **输出形态 = 类 Python 的函数调用序列**：LLM 每轮输出一段白名单调用，如 `seg("Alice", "Alice| 你好？")`（示例形态，非最终签名）。调用形态为已达成共识的方向，具体签名与参数形态为实现细节，由后续设计文档确定。
- **保留 Python 语法风格，含缩进与块结构语义**："类 Python"指完整语法形态，不限于调用签名——部分元素（如选项块、条件块）的解析依赖缩进/块结构确定归属与范围，此类语义是解析所需而非装饰。
- **执行语义绝不是 Python**：引擎绝不执行、求值、导入 LLM 输出——输出是"脚本"，引擎是只认白名单签名的解释器（见 §5.3 红线）。
- **组件语义以 Ren'Py 为词汇与范围参考**：`scene` / `show` / `play` / `menu` 等业界视觉小说通用语义构成词汇主体，保证规范性、全面性与业界对齐；引擎特有元素（存档、桥接、素材声明、状态变更）作为扩展成员与通用词汇并存。
- 引擎定义调用签名表（角色、对话、场景、音乐、声明、状态、选项、存档、桥接等），类似向 LLM 暴露的受控 API——**函数签名即格式规范**。

### 5.3 不变量（红线）

- **调用形态是 Python，执行语义绝不是 Python**——引擎绝不执行、求值、导入 LLM 输出；LLM 输出是"脚本"，引擎是只认白名单签名的解释器。
- 条件逻辑全部参数化，由引擎既有条件解析机制评估——LLM 无执行权，只有建议权（"本地数据是唯一真相源"原则的延伸）。
- 白名单签名即全部格式规范；新元素 = 新签名，扩展路径固定。
- 流式可解析：每行自包含，或可经引擎缓冲拼接；位置追踪由引擎自记。块结构语义与增量可解析的相容方式（块边界如何在流式下增量判定）由设计文档确定。
- 纯文本、模型无关——不同后端（云端 / 本地 / 未来专用模型）同一格式。
- 对话角色为结构化参数（不再依赖文本冒号解析），供立绘、语音等下游稳定消费。

### 5.4 验收标准

- 调用识别率（目标 ≥ 98%，经 Prompt Lab 实测校准）。
- 参数正确率（目标 ≥ 95%，经 Prompt Lab 实测校准）。
- TTFT 对比现行协议基线不劣化（目标：显著改善——用数据验证"类调用形态先验"假设）。
- token 开销在可接受上限内（现行协议量级估计约 10-15% 附加，实测确认）。

## §6 Phase 3 章程

### 6.1 定位

协议层重构，非功能扩展。产出 v3.0。当前已记录三个决策（§3-§5），后续决策按 §2 增量追加。**边界明确**：

| 不做 | 归属 |
|------|------|
| TTS、向量记忆、多人、云同步、剧本导出、变量语义扩展 | Phase 4 |
| UI 重构 | 前端仅适配新事件格式，不重设计 |
| 原生函数调用（tool calling）集成 | 可选方向，不交付；协议保持模型无关纯文本 |

**例外并入**：变量系统的**协议层面**定型（类型、条件参数化、上限演进）并入决策三——趁签名设计一次定型，避免二次升级。

### 6.2 总则

1. **度量先行**：每个决策必须有可量化验收指标，达标才推进。
2. **阶段落地**：每个决策独立验证、独立提交，互不阻塞。
3. **低风险先行**：每个决策以纯增量、兼容现行协议的验证步骤开头，保证任何时刻可回退。
4. **不破坏公理**：桥接约束（每轮一标记、标记后无交互）、本地数据唯一真相源、流式解析两要求（增量可解析、位置可追踪）——三条红线任何决策不得触碰。

### 6.3 里程碑

- **M1（地基）**：决策三——解析器 + Prompt Lab 实测达标。
- **M2**：决策一——轮 = 节点 + 上下文管理重设计 + 存档格式升级。
- **M3**：决策二——声明不阻塞 + 使用点等待 + 超时兜底。
- **M4（收官）**：格式约束解码——竞争分析标的最高优先计划项，决策三落地后顺水推舟，验证协议层重构的长期价值。
- **发布**：v3.0。

> 里程碑顺序可局部调整（如 M2 / M3 互换），但 M1 必须先行——格式是另两项的地基，其实测结果可能反哺另两项的细节设计。

## §7 Phase 4 改版

原 Phase 3"完整体验"（变量系统增强、向量记忆、多模型、云同步、TTS、剧本导出、多人模式）整体后移为 **Phase 4**。协议层重构完成后，各项功能实现反而更顺：

| Phase 4 功能 | 与协议层重构的关系 |
|--------------|---------------------|
| 剧本导出 | 直接消费"轮 = 节点"的确定性边界，幕/场结构即节点结构 |
| 向量记忆 | 节点级摘要永不缺失，是现成的向量化原料 |
| TTS / 音色冻结 | 对话角色为结构化参数，音色映射稳定 |
| 多人 / 云同步 | 节点级存档语义给出明确同步粒度 |
| 多模型 | 模型无关的纯文本协议已就位 |

**变量系统增强拆分**：协议层并入 Phase 3 一次定型（避免改签名）；语义层留在 Phase 4 自由演进。
